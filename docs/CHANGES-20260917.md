都是**不在原清单上**、做验证时才暴露的：

| # | 问题 | 怎么发现的 | 处理 |
|---|---|---|---|
| 1 | `reconcile_index_status.py` 缺 schema 兜底 → 旧库上因列不存在直接报错 | 首次跑脚本 | 补 `init_db(engine)`（幂等） |

| 3 | id 迁移漏了**评测集引用** → 指标会崩到 0 | 跑评测前检查 gold | 并入迁移脚本 |
| 4 | 评测口径盲区（带过滤掩盖图断裂） | 官方评测满分但已知退化存在 | 补 cross 口径 |
| 5 | **我自己报错了**：只比 MRR 就说"持平" | `compare_reports` 报出 precision 提升 | 订正报告 + 面试稿 |
| 6 | **回归门禁假警报率 100%**：延迟阈值量纲不匹配 | 跑全层评测报「有回归」，查下来是延迟噪声 | 按指标族分阈值策略（见下） |

> 💡 第 2、3 条都**只能靠跑真实链路发现**，单测和静态检查都覆盖不到。
> 第 5 条说明**单一指标得出的「无变化」结论不可信**。
> 第 6 条说明**门禁本身也需要被验证** —— 一个每次都报警的门禁等于没有门禁。

### 第 6 条详解：延迟阈值量纲不匹配

全局 `--threshold` 是**绝对值**（默认 0.02），只适配 0~1 的比率型指标。
对 `avg_latency_ms`（毫秒）而言 `abs(delta) >= 0.02` **恒成立**。

历史 6 次 real 运行实测：

| run | avg_latency_ms | pass_rate | 相邻 Δ | 0.02 绝对阈值判定 |
|---|---|---|---|---|
| 09-07 | 1421 | 1.0 | — | 基线 |
| 09-11a | 774 | 1.0 | -647 | 🟢 提升 |
| 09-11b | 932 | 1.0 | +158 | 🔴 回归 |
| 09-16a | 687 | 1.0 | -245 | 🟢 提升 |
| 09-16b | 581 | 1.0 | -106 | 🟢 提升 |
| 09-17 | 710 | 1.0 | +129 | 🔴 回归 |

**5/5 次被标记，质量全程未变** → 假警报率 100%，会训练人忽略回归信号。

**排除自身嫌疑**：新增的 `list_indexed_document_ids` 查询实测**中位 0.41ms**
（710ms 的 0.06%），`abs(129) >= 0.02` 的判定与本次改动无关。

**修法**（`eval/compare_reports.py`）：噪声指标族走 `_THRESHOLD_OVERRIDES`，
要求**相对与绝对变化同时超阈**：

```python
_THRESHOLD_OVERRIDES = {
    'avg_latency_ms': {'rel': 0.5, 'min_abs': 200.0},
}
```

| 判据 | 结果 |
|---|---|
| 历史 5 次自然波动（最大 ±45%） | 全部不显著 ✅ |
| 真实劣化（2 倍以上） | 全部显著 ✅ |
| 比率型指标 | 行为不变 ✅ |

测试 `tests/test_eval_compare_thresholds.py`（22 例），含**历史真实数据回归用例**。
README 的「阈值怎么定」段已同步订正（原文只说「方向判断内置、不用手动配」，
未指出绝对值阈值对毫秒级指标恒为真）。

## 八、设计决策与取舍

### 1. 版本化 id 顺序契约

```
先 upsert 新版本  →  再 delete_stale 旧版本
```
崩溃在两者之间 = **同内容重复（无害）**。绝不出现错误内容，也绝不全丢。
> 对比「先 delete 再 upsert」：崩溃会导致整本书搜不到。而**幽灵 chunk 是静默污染，比全丢更危险** ——
> 全丢时模型会诚实说查不到；幽灵会让模型自信地用错误语料作答。

### 2. `delete_stale` 用显式 id 列表而非 Chroma `where` 过滤

历史 chunk 缺 `content_hash` 键，`$ne` 对缺失键的行为跨版本不可靠 → 在 Python 侧过滤后按显式 id 删。

### 3. 表格：原子性 + 上限，两个都要

原子性防「丢表头」，上限防「炸 embedding」。**做了一半等于没做** ——
超限时按行分批且**每批重复表头**（参考 LlamaIndex table node parser / unstructured 的 header replication）。

### 4. 索引重建走蓝绿 + 上线前验证

```
写新集合 → 数量/id/向量校验 → 跑 golden → 若低于重建前则中止
```
任一步失败**不动旧集合**。因为重建本身有风险，不能"重建完再说"。

### 5. `cross_summary` 放顶层键而非嵌进 `summary`

`compare_reports.py` 会把 `summary` 里的 dict 型字段当「系统」展平，
嵌进去会污染下游对比。

### 6. P0-4 的启用顺序（关键）

**先迁移 → 再清洗状态 → 再重建索引 → 最后启用过滤。**
理由：那 3 个卡死文档的向量是完整的，若先启用过滤会被**误杀**（功能正常却查不到）。
该依赖已写进 `qa.py` 代码注释。

### 7. 存储向量 vs 弃用旧 id

未采用「加 `valid` 字段标记」方案 —— 那会让每次检索都多一次过滤，
且孤儿数据永久留存。版本化 id 是**内容寻址**，天然自描述。
