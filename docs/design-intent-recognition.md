# 多轮对话意图方案:从 qa_meta 到「上下文注入 + 检索门」

> 2026-09-08 · 触发场景:用户问「我上一个问题是什么?」——问题指向**会话本身**。
> 定位:本仓库的终局目标是**支持多轮对话**,不是只修这一句。方案按终局设计。

## 1. qa_meta(正则)为什么被推倒

旧实现 `utils/qa_meta.py`:句首锚定 + 枚举词表,几乎全部 pattern 以 `^我/^时间词` 开头,量词只收 `个|条|句|道`,序数不认「第 N 个」。真实对话大量漏判:

| 问法 | 漏判原因 |
|---|---|
| 请问我上一个问题是什么? | `^我` 锚定,口语前缀破坏匹配 |
| 那/对了/麻烦你…我上次问了啥? | 开场白不在词表 |
| 我上一轮/上一回问了什么? | 量词表无「轮/回/波」 |
| 我第一个问题问的是什么? | 序数词表无「第 N 个」 |
| 再上一个呢? | 省略主语的追问,完全没有 pattern |

两个结构缺陷:① **枚举法**只覆盖写进 pattern 的句式,补一个漏一个;② 元问题分支**早退不写回 chat_messages**,连续追问「那再上一个呢?」递归断链。

## 2. 目标重定义:支持多轮对话

真正要解决的不是"识别某几类句子",而是:**让问答系统拥有对话记忆,并让模型在记忆之上作答**。这样「上一个问题是什么」「第二个问题」「刚才说的展开讲讲」「这和前面矛盾吗」由**同一套机制**自然解决,而不是每个句式一条特判。

## 3. 终局方案 D:上下文注入(D 是主线)

### 3.1 数据基础已具备

- `chat_messages` 已按 session 存 user/assistant 完整记录(graph `record` 节点写入);
- 缺的只是:**读回**并注入模型,而不是永远单轮裸奔。

### 3.2 最小内核(第一里程碑)

```
QAState 增加 history: list[dict](最近 N 轮,截断)
build_qa_graph 首节点 context_load:
    ├─ 读 chat_messages(role=user/assistant, 倒序取最近 N 轮, 正序)
    └─ 写入 state.history
之后两个动作:
1. 检索门(retrieval gate,二元):这一轮要不要检索?
   模型看到注入的历史后自判 —— 纯历史问题/闲聊/寒暄 → 直接答,跳过检索;
   书内容问题 → 走原 retrieve/judge。
2. answer/judge prompt 注入「对话记录」区(只注入历史,原文片段仍是唯一事实源)
```

### 3.3 关键设计点(避免翻车)

- **答案从记录里读,不许模型凭记忆编**。「你上一个问题是:…」必须由注入的 transcript 生成——prompt 里明确:引用对话记录时按记录原文作答;记录里没有就说没有,不编造。这继承了 qa_meta 路由时代"查历史作答"的诚实性,但不再需要专门的回放服务。
- **检索门是二元判断,不是四分类 intent router**。多轮架构下"要不要检索"是唯一必须回答的问题;它可以在注入上下文的同一次 LLM 调用里顺带完成(输出需要检索 / 不需要),不额外增加一轮模型往返。方案 C 的"四分类路由"被吸收、简化成这个 gate——C 的合理内核没有丢。
- **缓存策略要随多轮调整**:`cache_check` 以单轮问法相似度判重,多轮后同一问法在不同前文语境下语义不同(「刚才那个」「继续说」),且历史/闲聊类不该写入也不该命中书内容缓存。里程碑内先做:历史注入存在的轮次跳过缓存命中? 或缓存键并入最近一轮指纹,再做评测取舍。
- **record 不变**:所有轮次(含被 gate 直答的历史轮)都写回 chat_messages,多轮递归自然成立。
- **截断与成本**:注入最近 N 轮(N 先取 2~4),超长会话用摘要压缩(后续课题)。

### 3.4 为什么这比 C(独立意图路由)更合理

- C 把「上一个问题」当**异常句式**特判;D 让**所有追问/指代/历史回忆**共享同一能力,句式泛化是免费的。
- C 的 history 回放服务是"第二套 QA 逻辑",和 RAG 并存,要维护两套答案风格;D 只有一套。
- C 无法回答「你刚才为什么那么说」「把上一段解释里的例子再讲一遍」这类**跨轮语义**问题;D 能。
- D 的代价是 prompt 变长(可截断/摘要)与缓存语义变化,可度量、可评测。

## 4. 候选对比(更新版,供决策留档)

| 方案 | 定位 | 判断 |
|---|---|---|
| A:LLM 四分类路由 | 每问一次 intent 分类 | 独立分类是过渡思路;被 D 的检索门吸收 |
| B:向量原型路由 | embedding 原型匹配 | 超短句弱;同样只是"路由",不解决跨轮语义 |
| C:规则+LLM 混合路由 | 快速止血 | **过渡可选**:不想动主链路时,2 天内可上线 |
| **D:上下文注入+检索门** | **终局** | **推荐主线**,直接按多轮架构走 |

## 5. 落地里程碑

(context_load/gate/context_answer 节点,history 注入 answer prompt),

1. **M1 上下文注入内核**:`history` 进 QAState;context_load 读回最近 N 轮;answer/judge prompt 注入对话记录;检索门直答不检索。跑通「我上一个问题是什么/再上一个呢/刚才说的展开讲讲」。
2. **M2 缓存与评测**:缓存键上下文化或按评测结果定策略;新增多轮 golden set(`eval/multi_turn_gold.json`),覆盖:历史回忆、指代追问、闲聊、澄清回复、书内容追问;扩展 `run_eval.py` 支持多轮回放。
3. **M3 长会话**:摘要压缩注入、成本/延迟观测。

## 6. 风险与待定

- 检索门判断错误 → 该检索没检索(答案浅)。缓解:gate 保守——拿不准一律检索;gold set 压误判率。
- 注入历史污染书答案(模型把对话当事实源)。缓解:prompt 分层——书内容只认原文片段;对话记录仅用于指代/回忆。
- 缓存误命中跨轮歧义。缓解:M2 专项评测。
- `docs/interview-qa-answers.md` 2026-09-08 条目④已随 qa_meta 删除失效,需改写为本次复盘。

## 7. 结论

终局支持多轮 → **D 是主线**;C 若为上线节奏需要可作为过渡,但其"路由"内核最终被 D 的检索门吸收,不重复造。
