# 工具参数被附加调用外壳标签（`</answer></invoke>`）——机制与出口清洗

日期：2026-09-24 · 触发：用户把 app 里的回答贴回来问「这类格式错误应该如何规避」

## 0. 现象

用户收到的回答正文末尾带着：

```
…最终是由昴日星官（本相为双冠子大公鸡）将其降伏，现出原形——一只琵琶大小的蝎子精[1]。</answer>
</invoke>
```

## 1. 定位：不是我们写进去的，是落在**工具参数**里的

- 全仓 grep（含 `config/prompt.yml`）搜 `</answer>` / `</invoke>`：**为空**。
- 库里同形态共 **3 条**（`chat_messages`，共 462 条消息）：

| id | session | 角色 | 形态 |
|---|---|---|---|
| 2874 | 1219 | assistant | 回答正文（用户贴回来的那条，199 字 + 残渣） |
| 2787 | 1177 | assistant | 「信息不足」说明文本 |
| 2861 | 1216 | assistant | 同上 |

**关键**：2874 走的是 `final_answer.answer`，2787/2861 走的是
`request_clarification.missing_info` —— **两个工具都中招**。
所以这不是某个工具的偶发问题，而是：
**工具参数字符串是唯一没有护栏的通道**。

- 实测该文本不含 schema 校验、不含格式约束，取出来直接进三个去向：
  API 响应、`chat_messages` 表、QA 缓存。
- 直接问模型要 `final_answer`（3 次、不带任何历史）：**3/3 干净** → 是**间歇性**的，
  不是稳定复现（这也解释了为什么它能潜伏到用户撞上）。

## 2. 为什么这不是「难看」而是缺陷：它会自我强化

带标签的文本一旦写进 `chat_messages`，此后每一轮的 prompt 历史里都带着它，
模型继续模仿自己上一轮的格式。`logs/qa_20260921.log` 的 `rendered history` 里能直接看到
带标签的历史被回放：

```
'助手：…就此把他赶走[2]。</answer>\n</invoke>\n'
```

于是形成**反馈环**：一次偶发 → 存库 → 每轮 prompt 带着它 → 模型继续这么写。
所以清洗必须**双向**：出口拦新的、入口中和存量。只做出口，环还在。

## 3. 修法：所有模型自由文本出口收敛到一个函数

新增 `utils/answer_text.py::sanitize_model_text`，挂在**5 个边界**上：

| 边界 | 位置 | 覆盖 |
|---|---|---|
| 出口 1 | `answer` 节点 | API 响应 + `chat_messages` + QA 缓存（一次清洗三处） |
| 出口 2 | `context_answer` | chat / history 意图的文本回答 |
| 出口 3 | `cache_check` 语义命中 | **存量**脏缓存 |
| 出口 4 | `cache_check` 精确命中 | **存量**脏缓存 |
| 入口 5 | `context_load` 组 prompt 的历史 | **存量**污染，断开反馈环 |
| 出口 6 | `GET /{session_id}/messages` | **用户可见面**：app 里往回翻的历史 |

出口 3/4 与边界 6 是「修好写路径 ≠ 干净」的那两半 —— 不清的话存量会一直可见。

### 判据刻意收得很紧

- **只剥首尾**、**只按白名单认标签**（answer/invoke/tool_call/function/parameter/…，
  允许 `antml:` 这类命名空间前缀）。正文中间的同类标签**不碰** —— 那是内容不是残渣。
  依据：回答正文里有 `[1]`、引号、破折号，也可能引用含尖括号的原文；
  在中间做「去掉所有 `<...>`」的正则会误伤正文。
- **不动用户消息**：用户输入里就算有这种标签也不替他改写（已用测试钉住）。
- **只构造响应对象，不改 ORM 实体**：历史接口是 GET，不该顺手往库里写东西 ——
  存量清洗走「读时中和」，不做破坏性数据迁移。
- **剥空则回退原文并告警**：本函数只管格式，不替调用方判断「这条回答是不是没内容」，
  更不能把非空回答变成空字符串（`</invoke>` 这种退化输入已用测试钉住）。
- 干净文本**原对象返回**（断言用 `is` 而非 `==`）：保证可以无脑挂在所有出口上。

### 两条被否掉的做法

1. **在客户端修**。2026-09-17 的教训已经写过：只改前端 = 把正确性寄托在
   「所有客户端都及时更新」上；而这里更糟 —— 污染是**存在服务端**的，客户端再多也清不掉。
2. **用「去掉所有 `<...>`」的正则**。会误伤正文（见上）。

## 4. 验证

- 新增 `tests/test_answer_sanitize.py`（**14 条**）：单元 8 条 + 出口/入口/历史/存量缓存路径。
- **反证**（关掉清洗后应当变红）：
  - 关掉 `answer` 节点那行 → `test_api_response_is_clean`、
    `test_stored_message_and_cache_are_clean` **2 failed**；
  - 关掉精确缓存命中那行 → `test_polluted_cache_hit_returns_clean_answer` **1 failed**；
  - 恢复后全绿。
- **对真实库那 3 条**跑清洗：残渣全部清掉，正文完整保留
  （346 → 326 字、219 → 199 字，少的正好是标签与换行）。
- 全量 **593 → 607 passed**，`ruff check src tests` 干净。

## 5. 「这类格式错误」以后怎么避免（回答用户的问题）

1. **把「模型自由文本 → 用户/存储」收敛到一个边界函数**。
   这次出事的根因不是某个工具写错了，而是**工具参数是唯一没有护栏的通道** ——
   有 schema 的地方（结构化字段）不会有这种问题，自由文本的地方必须有。
2. **边界要双向做**：出口（写库/返回）拦新的，入口（组 prompt）中和存量。
   只做出口，反馈环还在。
3. **凡是存下来的文本都是「用户可见面」**：历史接口、导出、缓存命中
   —— 每多一个消费者就多一个出口，漏一个就等于没修干净。
4. **白名单 + 只碰首尾**：清洗函数越宽越危险，宁可漏不可误伤正文。
5. **剥掉时要记日志**：`问答[出口清洗] 剥掉模型附加的调用外壳标签 [...]`
   —— 它是一个先行指标（模型/供应商侧在变的信号）。目前出现率约 3/462。
6. **别在客户端修**（2026-09-17 的教训）。
7. **测试必须反证**：把修的那一行关掉要能变红，否则只是「跑得通」。

## 6. 未做 / 边界

- **不做破坏性数据迁移**：3 条存量行仍带残渣存在库里，靠读时中和。
  如果以后有别的消费者直接读 `chat_messages`（导出、分析脚本），要么接同一个函数，
  要么那时再做一次收敛式清理。
- **只处理首尾**：如果模型以后把残渣吐在文本**中间**，本函数不管（会走 `logger` 之外静默通过）。
  现在的实测形态都是首尾，先按这个收窄。
- **出现率 3/462 是「用户可见的回答」之外的口径**：分母是消息总数，不是「经过工具的回答数」，
  所以不能当作真实触发率来用。
