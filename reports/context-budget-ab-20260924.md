# 历史窗口预算 A/B：4000 → 16000，并纠正一个用合成文本推出的错误结论

日期：2026-09-24 · 触发：用户问「上限 4000 token 是不是太少了，底层模型支持 1m 上下文窗口」。

## 0. 结论先行

| 配置 | 原值 | 新值 | 依据 |
|---|---|---|---|
| `history_token_budget` | 4000 | **16000** | 真实流量 146 会话：4000 截断 1/146，8000 起 0/146；被截断时端到端**自信答错** |
| `history_msg_token_cap` | 800 | **2000** | 实测 2/487 条真实消息超标（968 token 被砍约 17%）；2000 覆盖 max 且留 2× |

两处都不需要改代码就能覆盖：`Settings` 是 pydantic `BaseSettings`，
`HISTORY_TOKEN_BUDGET=16000` 即可 —— 实测有效（4000→32000、800→2400 都生效）。

## 1. 先纠正一个错误结论

「4000 只装 7 轮、15 轮那半段在溢出」是**用合成文本推出来的，与现实相反**。

`scripts/probe_window_capacity.py` 里的真实形态常量是「用户 21 字符 / 助手 392 字符」，
按它算是每轮 556 token、4000 装约 7 轮。但生产库 487 条真实消息实测：

```
用户消息 token：p50=14  p90=39  p95=49  max=54   mean=17
助手消息 token：p50=55  p90=288 p95=335 max=968  mean=111
```

**助手消息 p50 只有 55 token，合成文本按 520 算 —— 高估 7.2×。**
所以拿合成文本推容量会系统性低估窗口能装多少轮。容量必须用真实序列量。

## 2. 确定性测量（零 API、零噪声）

`scripts/probe_context_budget_ab.py` 直接用**生产库真实消息序列**跑 `_select_window`：

```
真实流量：146 个会话 / 487 条消息
  每会话消息条数：p50=2 p90=6 p99=24 max=25

  budget |         截断会话 |     中位保留 | 最长会话
    4000 | 1/146 = 0.7% |      2 条 | 25 条只留 25 条
    8000 | 0/146 = 0.0% |      2 条 | 25 条只留 25 条
   16000 | 0/146 = 0.0% |      2 条 | 25 条只留 25 条
   32000 | 0/146 = 0.0% |      2 条 | 25 条只留 25 条
```

**4000 在真实流量下只影响 146 个会话里的 1 个（0.7%）**，连最长的真实会话（25 条）都全装下。

## 3. 端到端 A/B

### 为什么必须新造夹具

现成夹具**结构上测不到**这个改动：

- `eval/multi_turn_gold.json`（11 条）**只断言 route**、最长 **6 轮**，窗口装得下；
  而且它用《三体》，语料里没有《三体》（只有《西游记》1332 块）—— 它刻意不碰内容。
- `eval/run_intent_eval.py` 只统计 `route_accuracy`。
- 所以 budget 从 4000 调到 32000，这些指标会**逐字相同**。不是改动无害，是夹具看不见。

### 无噪声用例设计

`scripts/probe_context_budget_e2e.py`：

- 第 1 轮用户：「请记住代号蓝鲸-7。」
- 填 12 轮，**用库里真实最长的助手回复**当填轮（长度分布真实，不合成）
- 末尾问「**我第一个问题是什么？**」—— 命中 `history` **规则快通道**
  （词表含「第一个问题」）→ **零 LLM 门、不走检索**，结果只取决于「第 1 轮原文在不在窗口里」
- 判据是确定性的：答案里有没有「蓝鲸-7」

### 结果

| | budget=4000 | budget=16000 |
|---|---|---|
| 会话总 token | 6266 | 6266 |
| 窗口保留 | 18/25 | 25/25 |
| 第 1 轮在窗口内（确定性） | ❌ | ✅ |
| 答案含代号（端到端） | ❌ | ✅ |
| 实际答案 | **「西游记第13回讲了什么？」** | 「请记住代号蓝鲸-7。」 |
| intent / channel | history / rule | history / rule |

**失败形态比「丢上下文」更糟**：4000 下模型没有说「记录里没有相关内容」，
而是把窗口里最老的一条冒充成「第一个问题」，**自信地给出错误答案**。
静默答错是这套系统里代价最高的一类失败。

## 4. 决策依据：预算是**上限不是配额**

这一点在上一轮对话里我说反了，纠正：

- 短会话**永远碰不到** 16000 → 调大对它们**零成本**；
- 只有真长到那一档的会话才付费，而那些会话恰恰需要上下文；
- 所以「截断占比降到 0」之后，再往上调只是空转上限 —— 不加分，也不花钱。

不取 32000：8000 已覆盖全部实测（含 6266 token 的最坏合成会话），16000 = 实测最坏 + 2.5× 余量。
再往上只抬高峰值 prompt，而本仓**仍没有**「整段 prompt 超模型上下文」的总量兜底
（见 `reports/answer-chunk-budget-20260924.md` §4.2）。

## 5. 顺带发现：`cap=800` 也在砍真实消息

实测 2/487 条真实消息超 800 token（都是 968 token 的长回复，被砍掉约 17%）。
助手 p95 才 335 → 800 这个值定得比真实分布低。取 2000：覆盖 max（968）且留 2×，
同时单条仍只占窗口的 12.5%，「防一条长回答吃掉整个窗口」的职责未失效。

## 6. 怎么复跑

```bash
# 确定性：真实库各预算的截断占比（零 API）
uv run python scripts/probe_context_budget_ab.py
uv run python scripts/probe_context_budget_ab.py --budgets 4000,8000,16000,32000

# 端到端：用环境变量切预算（这才是真实 A/B 姿势）
HISTORY_TOKEN_BUDGET=4000  uv run python scripts/probe_context_budget_e2e.py
HISTORY_TOKEN_BUDGET=16000 uv run python scripts/probe_context_budget_e2e.py
```

`probe_context_budget_e2e.py` 会在库里建会话并在结束时删除（含消息）。

## 7. 未做 / 边界（如实说明）

1. **样本只有 1 个用例、1 次运行。** 但该用例的判据是确定性的（窗口里有没有第 1 轮原文）
   + 无噪声路径（rule 路由、不检索），所以不存在「跑 8 次才能定论」那个问题。
   局限是**只覆盖了 history 回忆这一条路径**，没有测「早期实体被挤出后 CQR 抽不到实体」
   那条路 —— 那条理论上受影响更大，但需要造多轮 + 检索的用例，本轮没做。
2. **真实流量是本机开发库**（146 会话 / 487 消息），大概率主要是我们自己的测试会话，
   **不代表真实用户分布**。若上线后出现长会话，应重跑 `probe_context_budget_ab.py` 复核。
3. **未评估长上下文的退化风险**：16000 token 远未到「长上下文」区间，
   但若将来把 budget 提到 10 万量级，必须重新评估「塞满是否更容易被无关早轮带偏」。
4. **`probe_window_capacity.py` 里的合成文本常量没改** —— 它现在会给出与实际相反的轮数结论。
   本轮不动它（它是历史对照，改了会模糊 09-22 那次的证据），但在本报告里标注了该限制。
5. **没有把「窗口截断」打成可观测指标**。现在只有一条 `原文窗口 N 条（预算 …，取回 … 条）` 日志，
   没有聚合。理想做法：把「截断占比」做成先行指标，升上去就说明该重估预算。

### 一个方法论坑（我自己踩的，留注释钉住）

`_select_window` 返回的是 **dict 列表**，不是 `(role, content)` 元组。
我在探针里写成 `any(c == INTRO for _, c in kept)` —— 按 tuple 解包拿到的是**键名**
（`'role'`/`'content'`），于是这条「确定性」判据**恒为 False**，两组都报 false。
端到端那条（答案含代号）不受影响，才没把结论带偏。
**「确定性判据」一旦写错就是静默的错误数字**，比模型判据更危险（没有噪声来暴露它）。
