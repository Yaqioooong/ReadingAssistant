# 检索 agent：有界 ReAct + 工具化检索

> 2026-09-21 · 目标：解决「第一个妖怪是什么？特点？如何解决？」这类多问场景，**同时不拖累单问**
> 实现：`src/reading_assistant/graph/agent.py`（新）+ `graph/qa.py`（接线）+ `storage/vector_store.py`（工具能力）
> 评测：`eval/agent_gold.json` + `eval/run_agent_eval.py`（新）

## 1. 先定位置：它是「一次检索」与「问人」之间的台阶

```
gate → cache_check → retrieve → judge ──┬─ 有片段 → answer ──┬─ 够 → record
                                        │                    │
                                        └─ 空 ──→ agent ◄────┘ 不够
                                                    │
                                             仍不够 ↓
                                              create_hitl（今天的问人行为）
```

agent **只在原有链路走不通时才被拉起**，所以：

| 场景 | 走哪条路 | 额外成本 |
|---|---|---|
| 单问（「孙悟空的师父是谁？」） | retrieve → judge → answer | **0** |
| 一次检索空 / 模型判定不足 | + agent（≤6 步）| 若干次 LLM |

实测见 §4：简单题 **agent 触发率 0/5**。

## 2. 设计重心是**工具**，不是循环

2026-09-21 的实测把失败分成了两类，这决定了整个设计：

| 失败类 | 例子 | 单次检索能否救 |
|---|---|---|
| 查询里有实体 | 「寅将军是什么妖怪？」 | 能（只是被 `min_score` 挡） |
| **查询里没有实体** | 「第一个妖怪」「它的特点」「三问合一」 | **不能**（`min_score=0`、`k=200` 都捞不到） |

第二类要的是**换策略**，而策略来自工具。实测：只给 `search` 一个工具时，让模型改写查询，
**8/8 全部未命中** —— ReAct 退化成「昂贵的查询改写」。

### 工具集

| 工具 | 实现 | 为什么它能解决问题 |
|---|---|---|
| `search` | 既有 hybrid 检索（同 min_score、同白名单） | 语义召回，与主链路同源 |
| **`grep`** | **Chroma 原生 `where_document`** | 字面匹配，不依赖相似度。实测 `grep('寅将军')` **恰好 1 章**，而向量通道怎么调都取不到 |
| `list_chapters` | 元数据过滤，**不取正文** | `chapter_index` 是序数推理的唯一可靠依据 |
| `read_chapter` | 按章取全文，**不做相似度过滤** | 绕开 `min_score`（实测答案 chunk 余弦 0.4296 < 0.45 被误杀）|
| `finish` | 终止 | 由模型判断「够了」 |

**grep 的观察是「按章聚合 + 书内顺序」**，不是片段堆 —— 因为「第 N 个」需要的正是
「命中章集合 + 顺序」，而实测章级 embedding 排序的 margin 只有 0.037（不可靠）。
顺序必须来自 `chapter_index`（纯代码），不能来自相似度。

## 3. 三个「必须踩过才知道」的坑

### 3.1 OpenAI 兼容协议：tool_call 必须**逐条**回填

模型很自然地一轮返回多个 tool_call（实测 `search` + `list_chapters`）。只回一个，下一次请求直接 400：

```
BadRequestError: An assistant message with 'tool_calls' must be followed by
tool messages responding to each 'tool_call_id'. (insufficient tool messages)
```

即使 prompt 里写了「一次只调用一个工具」也不能指望它遵守。已改为逐条回填，
并加 `MAX_TOOL_CALLS_PER_ROUND` 上限（超限的也要回占位消息，否则同样 400）。

### 3.2 两种检索结果类型的字段名不一样

- `vector_store.SearchHit` → `id` + `metadata` 字典
- `rag.retriever.RetrievedChunk` → `chunk_id` + **扁平**字段，**没有 `metadata`**

只按一种写，`search` 工具每次都抛 `AttributeError`，而**工具级 try/except 把它变成
「工具执行失败」的观察** —— 表现为检索静默降级，日志上只是 `new_chunks=0`。
这类「被兜底吞掉的错」最难查，所以 `_to_chunk` 现在显式区分类型并统一形状。

### 3.3 Chroma 的 `where` 只能有一个操作符

```python
{'document_id': 7, 'chapter_index': 18}          # ✗ ValueError: Expected where to have exactly one operator
{'$and': [{'document_id': 7}, {'chapter_index': 18}]}   # ✓
```

**这条只在真实 Chroma 上炸** —— `InMemoryVectorStore` 自己线性过滤、不校验 where 形状，
所以单测全绿而线上 `read_chapter` 每次都失败。修完后序数题从 **2/3 → 4/4** 答对。

## 5. 规模与稳定性（「书的量级上去」）

做对的：

- **grep 走原生索引**，不是 `all_chunks()` 全扫 —— 全扫是 O(全库)，量上去第一个崩的就是它；
- `list_chapters` / `get_chapter` 都是元数据过滤，不把整本书拉进内存；
- **硬预算**：`agent_max_steps` 封顶 LLM 轮数，观察字符总量封顶（防单章全文撑爆上下文）；
- **只读工具** → 节点重放安全。这是把循环放在节点内部（而非图上新增环）的前提：
  `interrupt()` 恢复会**从头重跑节点**，图上的环会变成整圈重放；
- **每题至多进一次 agent**（`agent_used` 闸），避免成本乘以进入次数；
- **工具异常不冒泡** → 结构化错误交给模型自修正（项目既有原则）；
- **模型异常 → 回退**到已有片段，不让 agent 把整次问答带崩。

仍然存在、这次没动的规模风险（如实记录）：

1. **`_identifier_fallback` 仍调 `all_chunks()`**（实测 1520 chunk / 280ms）。
   100 倍语料下约 28s/次 —— **这是下一个该修的地方**，且它是既有代码，不是本次引入。
2. **`grep` 对高频词会物化大量行**（如「妖怪」全库数百处）。当前 `limit=400` 截断，
   观察也只列前 8 章 —— 但 `get()` 本身仍会把命中拉回来。量级上去应改为「先计数、按章取」。
3. 无 tool 级超时（只有整体预算）。

## 6. 安全回归：不是「没回归」，是**有提升**

同批次对跑（`CACHE_ENABLED=false`，现有 38 题 e2e，真实 LLM），
唯一变量是 `AGENT_ENABLED`：

| 指标 | agent 开 | agent 关 | 变化 |
|---|---|---|---|
| pass_rate | **0.947** | 0.895 | **+5.2pp** |
| answerable_accuracy | **0.939** | 0.879 | **+6.0pp** |
| citation_coverage | 0.939 | 0.909 | +3.0pp |
| hallucination_rate | 0.0 | 0.0 | 持平（未变差） |
| avg_latency_ms | 3635 | 2134 | **+1501ms** |

**读法**：agent 在既有集上也带来提升（不是只对那一道题有用），幻觉率没有变差；
代价是**平均延迟 +70%**。

⚠️ 两点如实说明：
1. 这 38 题是**难题偏重**的 gold 集（含「有人说…对吗」纠错题与「书里没写」的诚实题），
   agent 触发比例高于真实使用。真实单问场景实测**触发率 0**（§4.2），
   所以生产上的平均延迟影响应显著低于 70% —— 但**我还没有生产流量下的触发率数据**，不做定量断言。
2. 延迟是**语料平均**，无法从本次报告拆出「触发题 vs 未触发题」的分项；要精确归因需要
   按题粒度记录（`agent_report_*.json` 里已有单题 `cost_ms`，可作为下一步）。

## 6.5 subagent 有没有必要：按「是否解决已测出的瓶颈」判

判断标准不是「听起来更强」，而是**它是否解决了一个已经被测量出来的瓶颈**。
本次测出的瓶颈有三个，且**都不需要 subagent**：

| 测出的瓶颈 | 证据 | 本次用什么解决 |
|---|---|---|
| 检索策略单一 | 只有 `search` 时改写查询 8/8 失败 | 工具化（grep / read_chapter / list_chapters） |
| 正确段落余弦偏低被误杀 | 答案 chunk 余弦 0.4296 < `min_score` 0.45 | `read_chapter` 不做分数过滤 |
| 序数无法枚举 | 章级 embedding 排序 margin 仅 0.037 | `grep` + `chapter_index` 顺序（纯代码） |

三个候选 subagent 的逐个裁定：

**① 每本书一个 searcher（fan-out）→ 否。** 已有实测反证：
- 多书 fan-out 会**直接关掉缓存**（`len(document_ids) > 1` → `cache_channel='disabled'`），每问一次全价；
- 每本书只分到 `per_doc = max(2, ceil(top_k / 书数))` 个候选，书越多质量越差；
- 而**全库单次检索与指定单书的召回完全相同**（84.8% vs 84.8%，2026-09-20 实测）。
→ 收益为零、成本三项全亏。**明确不做。**

**② 校验 subagent（evaluator-optimizer）→ 暂缓，但留触发条件。**
本轮实测 `hallucination_rate` 多数为 **0.0**（仅在被否决的 `min_score=0.35` 配置下出现过 0.2），
可提升空间很薄，而代价是**每题 +1 次 LLM**。
**重启条件**：连续多轮评测 `hallucination_rate > 0.05`，或需要「严格引用模式」
（每个断言都必须能映射到某片段）时再做。

**③ 章节摘要 subagent → 不是 subagent，是离线批处理。**
实测章级摘要能把序数检索从 0.300 抬到 0.475，**是有效的**；但正确章 0.475 vs 错误章 0.438，
margin 仅 0.037 → 排序不可靠，必须与 `chapter_index` 顺序配合。
而 agent 现在的 `list_chapters` + `read_chapter` 组合已经达成了同样的效果（4/4 答对），
所以这件事的价值在于**离线预计算**（一次生成、长期复用），不在运行期多一个 agent。

**④ 查询规划 subagent → 不需要，它就是一次 LLM 调用。**
agent 的第一步已经在做这件事（`list_chapters` / `grep` 的选择本身就是规划）。

### 什么时候该引入 subagent（先看这些指标，不要凭感觉）

| 先行指标 | 阈值信号 | 该加什么 |
|---|---|---|
| `stopped_by='budget'` 占比 | 随语料增长而升高 | agent 容量不足 → 拆 per-book searcher |
| `agent_steps` 分布 | 大量集中在 `max_steps` | 预算不够或任务该分片 |
| `hallucination_rate` | 持续 > 0.05 | 校验 subagent（evaluator-optimizer） |
| 跨书问题占比 | 明显升高 | 跨书综合 subagent |

这套指标已经在本次实现里可观测（`agent_used` / `agent_steps` / `agent_actions` 已透出到
`AskResponse`，`agent_trace` 含每步动作与耗时），所以**先把指标跑出来再谈拆分**，
而不是先拆再说。

### 两处必须如实说明

1. **`ag-compound-01`（用户报的那道）本次没触发 agent 也通过了。**
   说明 gold 的判定（`expect_contains: 寅将军`）**不足以证明 agent 的价值** ——
   单次检索链路也可能答出这个实体。
   更强的证据是 §6 的 e2e A/B（agent 开/关：pass_rate +5.2pp）与 §4.1 的 4/4 复跑。
   这条 gold 的判定应当收紧为「三个子问题都被回答」，是下一步要改的。
2. **`ag-pronoun-02` 失败**（「他是怎么被收服的？」）。agent 跑了 3 步（grep + read_chapter）
   但答案里没有期望的 `孙悟空`。代词解析这一类**仍是缺口**：agent 能看到历史，
   但没有被明确要求「先把指代替换成实体再检索」。
   这正是 §6.5 里「代词类需要一次改写」那条的残留 —— 下一步该在 agent 的 system prompt
   或前置步骤里显式加上指代消解。

## 6.8 第二轮：用户实测失败后的三处修复（2026-09-21 16:56）

### 失败现场

用户在真实使用中又跑了「第一个妖怪」那道题，**Agent 跑了 4 步却答错、并最终转澄清**：

```
step1 grep 黄风怪 / grep 灵吉菩萨        ← 锚定在了两个「候选」上
step2 read_chapter 25
step3 read_chapter 26
finish  reason=「已定位第20-21回原文：第一个妖怪是黄风岭的黄风怪」
```

三个可疑点：① 结论（黄风怪）错；② `reason` 声称「第20-21回」却读的是 25/26 回（自相矛盾）；
③ 它贡献的 28 条片段把上限占满，**原有检索结果被整体挤出**。

### 数据：失败不是随机的，是被「初始检索」带偏的

对同一问题做首次向量检索，结果**9 条里 0 条含「寅将军」**，却有两条第 25 章（第二十回黄风岭）：

```
章序 25《第二十回 黄风岭唐僧有难》 ← 含黄风/虎先锋
章序  2《前言》
章序 36/91/44/92/97/37 …
含寅将军的条数: 0     含黄风/虎先锋的条数: 2
```

问法像「妖怪故事」，所以语义检索把**黄风岭**排到了前面 —— Agent 顺着它走，就答成了黄风怪。
**「检索给的内容」不等于「书里最早的」**，而旧 prompt 没有把这条说清楚。

### 一个反直觉的关键事实

| 词 | 在第十三回（寅将军）出现次数 |
|---|---|
| 妖怪 / 妖魔 / 妖精 | **0 / 0 / 0** |
| 妖邪 | 2 |
| 魔 | 12 |

也就是说 —— **「grep 一个类别词来枚举」这条策略本身就不可行**：
第十三回整章不含「妖怪」，用类别词搜会把它整章漏掉，然后把推理引向第三回或第十六回。
（我上一版 prompt 恰恰教的是「grep 类别词」，是错的 —— 已改。）

### 三处修复

**① `grep` 观察区分「正文回目」与「前后附文」**（确定性，交给代码）
- 判据：章名形如 `第…回` → 正文；前言/修订说明/附录/版权页 → 非正文。
- 命中按书内顺序列出，**最早一回直接标注 ★★★**；前言单独归入「非正文，不计入第几个」。
- 实测：未排除时「前言」含「妖怪」，会成为「最早命中章」把推理带偏。

**② `grep` 支持一次比较多个候选（新能力）**
- `grep("寅将军,黄风怪,黑熊精")` → 观察里直接给出【候选比较】，**按「最早出现在正文的位置」排序**。
- 「第几个」本质是**比较先后**，让代码算比让模型心算可靠（失败现场里模型把 25/26 回说成「第20-21回」）。
- 实测输出：
  ```
  1. 「寅将军」最早出现于 chapter_index=18 《第十三回…》  ★★★ 最早，就是它
  2. 「黑熊精」最早出现于 chapter_index=22 《第十七回…》
  3. 「黄风怪」最早出现于 chapter_index=25 《第二十回…》
  ```
- prompt 同时改成强制流程：**列 2~4 个具体候选名 → 一次查完让工具比较 → 读那一章**，
  并明写两条禁令：不要只用类别词；不要把初始片段当依据。

**③ 合并策略：Agent 片段不得清空原有片段**（`merge_agent_chunks`）
- 原来「Agent 在前 + 截断到上限」= Agent 走错方向时会**销毁原有证据**，
  把「Agent 失败」升级成「Agent 失败且上下文更差」。
- 现在预留 `cap//2` 个名额给原有片段（原有片段是 pre-agent 流水线的产出，Agent 的是推测性的）。

### ⚠️ 一处自我更正与一处诚实边界

1. **我更正了一个错误结论**：本轮中途我报过「50% 失败率（3/6）」——那是**缓存污染的假数据**
   （探针没禁缓存，第 2~4 次命中缓存直接返回、根本没走检索）。禁缓存后 6/6 全对。
   **同一个坑我在这个项目里踩了第二次**（第一次是 2026-09-20 的 top_k A/B）——
   凡是跑 A/B 或统计，必须先 `CACHE_ENABLED=false`。
2. **我没有可复现的失败基线**：修复前用干净探针跑，这台机器上也是通过的。
   所以本次**给不出「修复前 x% → 修复后 y%」的对比数字**。
   修复的依据是三条而非统计：① 用户的真实失败被机制解释清楚；
   ② 旧流程在「第十三回不含『妖怪』」这个事实上**结构性地不可能**得到正确答案；
   ③ 轨迹证明模型现在确实在用新能力。
   要拿到硬对比，需要构造一组序数题（≥20 道）做 before/after —— 已列入下一步。

## 6.9 第三轮：merge 排序 bug —— Agent 找对了，却被我丢掉了（2026-09-21 17:11）

### 失败现场（这道题已经能答对，但答不出来）

用户实测「唐僧收孙悟空为徒后，孙悟空消灭的第一个妖精是谁？它的技能是什么？」。
日志里 Agent **完全正确**：

```
finish  reason=已通过 grep 候选比较确认：…最早被悟空打死的妖精是第十七回的黑风山白衣秀士（白花蛇怪）
问答[agent] steps=5 stopped=finish finished=True chunks=16
问答[agent] 合并后 16 条（其中原有 8 条）
```

**但 answer 紧接着又判「信息不足」并转澄清。** Agent 明明找到了答案。

### 我的 bug：`merge_agent_chunks` 取的是「前 8 条」

Agent 本轮贡献 **28 条**（step1 grep 8 + step2 read_chapter 6 + step3 6 + step4 grep 8），
上限 16 条，预留 8 条给原有片段 → Agent 只得 8 个名额。
旧实现按**顺序**取前 8 条 → 全是 **step1 的宽网候选**，
而**真正含答案的 step2（read_chapter 22）与 step4（grep 白衣秀士）被整批丢掉**。

```
step1 grep(黑熊精,白花蛇怪,白骨夫人,黄风怪,虎先锋,凌虚子,玉龙)  ← 只有这批留下了
step2 read_chapter(22)   ← 第十七回，含答案，被丢
step3 read_chapter(21)
step4 grep(白衣秀士,白花蛇,禁箍,黑缨枪,化风)  ← 含答案，被丢
```

→ answer 看不到结论依据，只能再次说「信息不足」。**Agent 找对了，是我把它丢掉的。**

### 修复：Agent 片段按「后出优先」

轨迹是**收敛**的：后面的观察建立在前面之上，越晚的越接近结论。
所以 agent 片段改成 `reversed` 取尾部；原有片段仍保持原顺序（召回导向）。

### 修复效果（禁缓存，同一题 3 次）

| | 修复前 | 修复后 |
|---|---|---|
| 转澄清 | 必然 | **0/3** |
| 上下文含答案片段 | 0 条 | 2/16 或 0/16 |
| 答对 | — | **1/3** |

**改善是确定的：不再转澄清。但答案仍不稳定**，在两种之间摇摆：

| 次 | 答案 | 对错 |
|---|---|---|
| 1 | 白衣秀士（白花蛇怪，第十七回） | ❌ 晚三回 |
| 2 | **猛虎/虎精（第十四回）** | ✅ |
| 3 | 白衣秀士 | ❌ |

### 正确答案核实（不是猜的）

第十四回原文：「却说那孙行者请三藏上马…过了两界山，忽然见**一只猛虎**，咆哮剪尾而来…
被他照头一棒，就打的脑浆迸万点桃红」→ 剥皮做虎皮裙。
**所以收徒后第一个被消灭的妖精是那只虎精**，白衣秀士（第十七回）晚三回。

### 剩下的问题（下一层，未修）

Agent 的候选枚举依赖**模型对这本书的先验知识** —— 它的 grep 候选是
`黑熊精,白花蛇怪,白骨夫人,黄风怪,虎先锋,凌虚子,玉龙`，**没有第十四回的猛虎**。

→ **改进方向：锚点感知。** 本题给了一个明确锚点事件（「收孙悟空为徒」= 第十四回）。
正确策略应是：**先定位锚点事件所在章 → 从该章往后顺序扫**，而不是凭先验列候选名。
这比「猜候选」可靠得多，且同样不需要循环。

## 6.10 锚点感知：实现了、**实测回退**、已撤销（2026-09-21）

针对 §6.9 留下的问题（Agent 靠先验知识列候选名 → 漏掉第十四回那只猛虎），
我实现了「锚点感知」：新工具 `locate_event(term)` —— 定位锚点事件所在回目，
并给出「从该回起、按书内顺序的接下来 N 回」目录；prompt 里加了强制的【带锚点流程】。

**思路是对的**（按回目顺序扫，而不是按语义相似度猜），**但实测明确回退：**

| 指标 | 锚点流程前 | 加入锚点流程后 | 撤销后 |
|---|---|---|---|
| 答对（猛虎） | 1/3 | **0/4** | 1/4 |
| 转澄清 | 0/3 | **4/4** | 1/4 |
| Agent 动作 | 正常 | **`locate_event` 占 3~4 步（反复重试）** | 正常 |

### 根因：定位锚点本身又是一次「词汇鸿沟」

用户问「唐僧**收孙悟空为徒**后…」，但正文第十四回的回目是「**心猿归正**」——
「收孙悟空为徒」这个说法在原文里**不存在**。
于是 `locate_event("收了孙悟空")` 返回「没找到」，模型换个说法再试，
**3~4 次重试把 6 步预算耗尽**，根本没机会去读正文。

这才是真问题：**要定位锚点，就得先把「收孙悟空为徒」映射到「心猿归正」——
而这正是我前面一直在说的词汇鸿沟。** 锚点定位不解决它，反而又踩一遍。

### 处理：撤销，并留下记录

- prompt 恢复为「多候选枚举流程」，**移除强制的带锚点流程**；
- `locate_event` 代码保留但**刻意不加入 `AGENT_TOOLS`**（不暴露给模型），
  并在代码里写明为什么以及复活条件；
- 已复测确认撤销后回到 1/4 答对、1/4 转澄清（对比锚点版的 0/4、4/4）。

### 结论（这一轮最有价值的一条）

> **给 agent 加能力之前，先确认那个能力的**前提**在这个语料上成立。**

我这次的错误是：假设「锚点事件能用字面匹配定位」——而该假设在中文古典小说上不成立
（同一件事，问法与原文用词往往不同）。
能力本身逻辑没问题，**前提错了**，所以它不但没帮助，还挤掉了原本能用的步骤。

**复活条件**：先有「锚点事件的语义定位」（例如章级摘要上做匹配，而不是字面 grep）。
在那之前，暴露 `locate_event` 只会让模型把预算浪费在重试上。

### 仍然未解决（§6.9 的原问题还在）

Agent 的候选枚举仍依赖模型对这本书的先验知识，所以答案在这几种之间摇摆：
`猛虎`（对）/ `白衣秀士`（晚三回）/ `六贼`（不是妖精）。这是**下一层**要处理的，
而且它和整个项目反复出现的「词汇鸿沟」是同一个根。

## 6.11 「日志里已经检索到了，为什么结果模棱两可」—— 三层截断（2026-09-21）

用户问：小雷音寺那题，日志显示 agent 的 `finish reason` 明明写对了
（「妖怪为黄眉大王…来历是弥勒佛面前司磬的黄眉童儿…最终由弥勒佛设瓜田」），
为什么最终答案是「片段中并未出现该妖魔的名字与来历」？

### 答案：**agent 找对了，被三层截断吃掉；而且真正致命的那层在 merge 之前。**

排查过程（每次都是「先怀疑 A，插桩后发现是 B」）：

| 层 | 怀疑 | 插桩后的事实 |
|---|---|---|
| ① merge 排序 | 又丢了 agent 的片段？ | 分层生效：出 16 条 `{read_chapter: 6, grep: 2, None: 8}` ✓ |
| ② read_chapter 内容 | —— | **`found[:6]` 只回前 6 段**；而第六十六回的谜底全在第 8 段 |
| ③ **循环内截断** | —— | **`deduped[:budget.max_chunks]` 在 merge 前就截到 16 条，且取最先累积的** |

**③ 才是致命的**。实证：工具共贡献 **31 条**（grep 8 + 章A 11 + 章B 12），
到 merge 只剩 **16 条**（grep 8 + 章A 的前 8）——
**agent 随后读到的第二章（含答案的那一章）根本到不了 merge**。

### 三处修复

**① `read_chapter` 不再截成「前 N 段」**（整章返回）
原 `found[:6]` 的致命性有精确证据：
```
第六十六回（小雷音寺）共 12 段
含「黄眉」的段序号: [3, 6, 8]
含「司磬」「童儿」「人种袋」「瓜」的段序号: [8]   ← 谜底全在第 8 段
→ [:6] 正好把它切掉
```
章内 chunk 是切分产物、顺序＝书内顺序，**答案没有理由偏在前半章**。

**② 循环内不再截断**（`run.chunks = deduped`）
职责划分：**累积不设限**（只是些轻量 dict），**最终裁剪只由 `merge_agent_chunks` 负责**
—— 它知道来源优先级与「给原有片段留名额」；在这里截断只会让它拿不到完整信息。

**③ 整章合并为「分段」**（新增 `coalesce_chapter`）
一章 11~12 个 chunk，而 agent 只有约 8 个名额 —— **整章塞不下**，
丢哪段取决于顺序（靠运气）。合并成 ≤4000 字/段后，**一章只占 2 个名额**且文本完整：
```
修复前：chapter 71 → 11 条, chapter 72 → 12 条（共 23 个名额）
修复后：chapter 71 →  2 条, chapter 72 →  2 条（共  4 个名额，字数 7162/7220 完整）
```

### 效果（禁缓存）

| 题目 | 修复前 | 修复后 |
|---|---|---|
| ③ 小雷音寺（用户报的） | **3/5** | **5/5** |
| ① 全书第一个妖怪 | 1/3 | **3/3** |
| ② 收悟空后第一个妖精 | 1/3 | 2/3 |

关键中间量：**最终上下文里含「黄眉」的片段从 `0 条` → `7 条`**；
agent 步数也从 4~6 降到 3。

### ② 仍然最弱（2/3），原因与 §6.10 同源

它的失败不在检索通道，而在**候选枚举依赖模型对这本书的先验知识**
（agent 凭记忆列的候选漏了第十四回那只猛虎）。
这与「锚点感知」想解决的是同一件事，而锚点感知已实测回退（§6.10）——
所以这条留给「章级摘要索引」那条线，不在本轮再打补丁。
