# 检索深度：从「取消图书选择 + ReAct」到「把 top_k 调大」

> 2026-09-20 · 起因：问「取消当前图书选择逻辑，能否加入 ReAct 和多轮检索？」
> 结论：**真正该改的是一个配置项，不是架构。** 过程中还揪出两个让实验静默失效的基础设施 bug。

## 1. 先纠正前提：不选书已经是现状

前端 `ChatPanel.vue`：`const selectedDocIds = ref([]) // 空数组 = 全部书籍`，
且有「全部书籍」选项（`@click="selectedDocIds = []; scopeOpen = false"`）。
所以 **「不选书」不是要新增的能力，而是默认路径**，后端 `document_ids=[]` → 单次全库检索。

实测（33 道可测题）：

| 模式 | 召回 |
|---|---|
| 指定书 | 84.8% |
| **全库（不选书）** | **84.8%** |
| 便宜路由后（每书取最高分 argmax 选书） | 84.8% |
| **路由选对书** | **100%** |

- **取消选书在召回上零代价**；而「猜对是哪本书」这个动作空间**已经 100% 解决**。
- 一个重要更正：我原先猜「少数派书（doc5=181 chunk，11.9%）会被大书（doc7=1332 chunk，87.6%）挤掉」——
  **实测不成立**：用自身原文当 query 做全库 top6，两本书都 12/12，名次全是第 1。
  稠密检索按相似度排序，不吃语料占比。
- 缓存层面还有一条硬约束（2026-09-18 已报告）：`len(document_ids) > 1` 会**直接关掉缓存**。
  所以别做 fan-out；全库或路由都是单次检索 + 缓存可用。

## 2. 真正的失败不是「多跳」，是词汇鸿沟

doc7（西游记，87.6% 语料）20 道题，top6 命中 15/20（75%）。挂掉的 5 道里 **4 道是专名**：

| 问题（口语描述） | 期望答案（稀有专名） |
|---|---|
| 殷小姐当年是用什么方式选中陈光蕊做丈夫的？ | 抛打绣球卜婿 |
| 狮驼岭那个能装人、连大圣也吃了亏的宝贝叫什么？ | 阴阳二气瓶 |
| 天竺国那个假公主究竟是什么妖精变的？ | 广寒宫捣玄霜 |
| 取经功成后，那匹一路驮唐僧的白马被授了什么职名？ | 八部天龙马 |

查询向量落在「描述」附近，答案落在「专名」附近 —— **同一个 embedding 再搜十轮也到不了**。
**ReAct 救不了这个**，它不是推理深度不够，是词汇鸿沟。

## 3. 我自己的方案被自己的对照实验否掉了

先测「答案距命中 chunk 多远」（章内 chunk 序号差）：

| 情况 | 数量 |
|---|---|
| top6 直接命中 | 15/20 (75%) |
| **top6 未中，但答案就在已命中的某一章里** | **3/20 (15%)** |
| 导航方向都错 | 2/20 (10%) |

章内距离：0 chunk×14、1×2、2×1、7×1 —— 于是设计「邻近扩展（±N chunk）」，看着很对。

**但同预算对照实验把它否了：**

| 策略 | 召回 | prompt 字符 |
|---|---|---|
| top_k=6（现状） | 75.0% | 3916 |
| **top_k=16** | **85.0%** | **9176** |
| top_k=30 | 90.0% | 15679 |
| top_k=6 + 邻近±1 | 80.0% | 9142 |
| top_k=6 + 邻近±2 | 85.0% | **12981** |
| top_k=6 + 邻近±3 | 85.0% | 16151 |

**同样 85%：加大 top_k 花 9176 字符，邻近扩展花 12981 —— 贵 41%。**
原因：邻近扩展把 6 个命中点各扩 4 个邻居，大量重复冗余；top_k 全局按相似度取，无冗余。
**结论：不用写代码，改配置。**（差点实现一个更差的方案。）

## 4. ⚠️ 两个让实验静默失效的基础设施 bug

第一次 A/B 跑完，两组指标**逐字完全相同**（`pass_rate` 0.816、`answer_relevancy` 0.8474 到小数点后 4 位）。
不是巧合，是两层 bug 叠加：

### 4.1 A/B 被缓存污染

第二组 73/73 全部 `问答[缓存] 精确命中` —— 复用了第一组写的答案，38/38 逐字相同。
**A/B 评测必须禁缓存**（`CACHE_ENABLED=false`）。

### 4.2 `load_dotenv(override=True)` 让命令行配置静默失效（已修）

`src/reading_assistant/model/factory.py:12` 原本是 `load_dotenv(override=True)` ——
它把 `.env` 的值**强写进 `os.environ`**。而 `get_settings()` 是 `@lru_cache`，**谁先调用决定读到哪一份**：

- `uv run python -c "get_settings().top_k"` → 先读命令行 → `16` ✓
- `run_all --only e2e`（`create_app` → 建图 → import `model.factory` → `load_dotenv(override=True)`）
  → `os.environ` 被改回 `.env` 的 `6` → **`TOP_K=16` 与 `CACHE_ENABLED=false` 双双失效** ✗

证据：`import create_app` 之后 `os.environ['CACHE_ENABLED']` 从 `'false'` 变成 `'true'`。
**所以那个「A/B 无差异」的结论是假的 —— 两组跑的是同一配置。**

**修复**：`load_dotenv()`（默认 `override=False`），即标准约定「进程环境变量 > .env > 默认值」，附长注释。
**回归** `tests/test_settings_precedence.py`（2 条）—— 必须**跑子进程走完整 import 链**才测得出
（直接单测调 `get_settings()` 测不到，那时 `load_dotenv` 还没跑）。含反向保障：`.env` 仍要能补缺失键。
**已反证**：临时改回 `override=True` → 测试输出 `-16 / +6` 失败；恢复后通过。

## 5. 修复后的真实结论

`CACHE_ENABLED=false`，两轮独立跑，真实 LLM（DeepSeek）：

| | pass_rate | answerable_accuracy | citation_coverage | hallucination_rate |
|---|---|---|---|---|
| 第 1 轮 TOP_K=6 | 0.842 | 0.818 | 0.939 | 0.200 |
| 第 1 轮 **TOP_K=16** | **0.974** | **0.970** | 1.000 | 0.000 |
| 第 2 轮 TOP_K=6 | 0.816 | 0.788 | 0.939 | 0.000 |
| 第 2 轮 **TOP_K=16** | **0.921** | **0.909** | 0.939 | 0.000 |
| **6 组均值** | 0.829 | 0.803 | 0.939 | — |
| **16 组均值** | **0.948** | **0.940** | 0.970 | — |
| **变化** | **+11.9pp** | **+13.7pp** | +3.1pp | 见下 |

- 两轮方向一致，且**区间不重叠**（16 组最低 0.921 > 6 组最高 0.842）。
- 两组答案逐字相同仅 4/38 → 确认各自真跑了。
- 延迟几乎不变（2290ms → 2353ms）；prompt 约 3916 → 9176 字符。
- **幻觉率**：第 1 轮 0.2 → 0，第 2 轮 0 → 0 —— 提升方向正确但**单轮数据不足以定论**，不作硬结论。

### 增益来自哪（不是专名题）
e2e 的 21 道西游记题与检索 gold **零重合**（0/21），题型是「有人说…对吗？」纠错题
与「菩提祖师的师父是谁」这类**书里没写**的题。所以增益机制更可能是：
**更多上下文让「核对书中真实交代」和「确认书里确实没写」都更可靠** —— 而非命中某道专名题。
这也与 `retrieval_mode=hybrid` 的候选池（`hybrid_pool_size=50`）相符：
**正确的片段常已在池内，只是被 `k` 截掉了 —— 所以调 k 比调检索算法更划算。**

## 6. 落地

三处配置改一致（`k: 6` → `16`）+ YAML 里写明依据：

- `.env`（当前生效）
- `.env.example`（新部署）
- `src/reading_assistant/config/chroma.yml`（无 .env 时的默认值）

## 7. 没做的与为什么

- **ReAct / 有界多步循环：没做。** 真正需要多步的只有 2/20 题（10%），
  **样本量不足以支撑设计一个循环**；而循环要处理 `max_iterations`、中断恢复重放、
  成本上限，收益却不明确。要做得先建多跳 gold 把「该不该做」量出来。
- **邻近扩展：不做**（同预算下比 top_k 贵 41%，见 §3）。
- **多书 fan-out 的缓存问题**：仍存在（>1 本即禁用缓存），本次未动 ——
  但 §1 已说明全库是更优路径，这个坑可以绕开。

## 8. 复现

```bash
# 关缓存是必须的，否则第二组复用第一组
CACHE_ENABLED=false TOP_K=6  uv run python -m eval.run_all --mode real --only e2e --no-compare
CACHE_ENABLED=false TOP_K=16 uv run python -m eval.run_all --mode real --only e2e --no-compare

# 配置优先级回归
uv run python -m pytest tests/test_settings_precedence.py -q
```
